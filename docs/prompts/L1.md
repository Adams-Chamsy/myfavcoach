Quinze prompts, dans l'ordre. **Un prompt à la fois.** Après chacun : tu lances la commande de

## Ce que L1 ajoute au dépôt

Un backend réel, une identité réelle, et les six écrans du parcours d'entrée. À la fin du lot,
un inconnu crée un compte, vérifie son adresse, remplit son onboarding, ouvre un espace coach,
passe de l'un à l'autre, modifie ses informations et se déconnecte — avec des données protégées
par des politiques que tu as vues échouer avant de les voir passer.

**Ce que L1 ne touche pas** : offres, abonnements, paiement, vérification d'identité du coach,
messagerie, notifications. `EXPO_PUBLIC_STRIPE_PK` est déclarée et **reste inutilisée**.

## Les quatre règles de conduite, tirées de L0

Elles sont rappelées dans les prompts concernés. Elles viennent de ce qui a coûté du temps au
lot précédent.

**1. Un point d'arrêt annoncé n'est pas optionnel.** Quand un plan dit « je m'arrête ici et
j'attends ta validation », il s'arrête. Pas de « j'ai continué car c'était évident ».

**2. Toute nouvelle surface va dans la galerie, exercée dans les deux thèmes.** Une surface
absente de la galerie n'est pas vue par `npm run test:a11y` : c'est un angle mort, pas une
omission bénigne.

**3. Aucun fichier de test dans `app/`.** `_layout.test.tsx` devient une route pour
expo-router. Les tests de routage vivent dans `src/test/routage/` et se nomment
`layout-client.test.tsx`, `garde-session.test.tsx`.

**4. La preuve, pas l'affirmation.** Trois faux verts ont été trouvés en L0, un quatrième en L1
(P1.5), un cinquième en P1.11 :

| Faux vert | Ce que le prompt exige désormais |
|---|---|
| `fireEvent` non attendu : le test passe avant que l'interface ait réagi | Tout geste est attendu (`await`), toute assertion sur un rendu asynchrone utilise une requête qui attend. Un test qui passe sans `await` sur un geste asynchrone est réputé faux |
| `restoreAllMocks` non fiable : un test en polluait un autre | Aucun test ne dépend d'une restauration globale. Chaque test construit ses propres doublures et les démonte lui-même. Pour l'authentification : **injection par le fournisseur**, pas de substitution de module |
| Une liste d'exclusion qui ne protégeait rien | Toute protection par configuration est prouvée par un test qui **tente l'interdit et échoue**. Une règle non éprouvée est une règle absente |
| Un banc RLS entièrement vert (`npm run test:rls`, P1.5) sans qu'aucune de ses politiques n'ait jamais montré de rouge | 3 politiques sur 10 n'étaient exercées par aucun scénario — supprimer `comptes_select_soi`, `comptes_update_soi` ou `profils_client_update_espace_client` ne faisait rougir aucun test. **Une politique RLS n'est réputée testée qu'après avoir été cassée et avoir produit un rouge nommé.** Un banc vert ne prouve rien tant que chaque politique n'a pas montré son rouge — casser-restaurer politique par politique est obligatoire, jamais un échantillon |
| Une assertion `toHaveBeenCalledWith(...)` sur un mock, écrite dans le même commit que le code qu'elle teste (`src/services/auth/supabase.test.ts`, `inscrire`, P1.11) | Trouvé après P1.11 : `envoyerCourrielInscription` envoyait `date_naissance` en camelCase (jamais lu par le déclencheur serveur, qui attend le snake_case) — l'inscription réelle échouait donc TOUJOURS, sans qu'aucun test ne rougisse. Le test mocké vérifiait fidèlement que le mock avait reçu ce que le code envoyait, casse comprise : même main, même hypothèse fausse, des deux côtés de la même assertion. **Une assertion sur ce qu'un mock a reçu, écrite dans le même commit que le code qu'elle teste, ne prouve rien sur ce que le serveur attend. Ce qui traverse une frontière — nom de colonne, nom de champ, forme de charge utile — se prouve contre la vraie frontière ou ne se prouve pas.** |

Et la règle générale : **avant de me dire qu'un test est vert, casse volontairement ce qu'il
teste et montre-moi la sortie rouge.** Un test qui ne peut pas échouer ne teste rien.

## Le décor technique du lot

À connaître avant le premier prompt. Ces éléments sont figés, ils ne se rediscutent pas dans un
prompt.

| Sujet | Décision |
|---|---|
| Backend | Supabase, région Paris `eu-west-3` |
| Projets | **Deux**, `myfavcoach-dev` et `myfavcoach-prod`, séparés, jamais mélangés |
| Plan | Gratuit en développement, Pro avant le lot L4 |
| RLS | Activée automatiquement à la création des tables |
| Exposition | L'ajout automatique des nouvelles tables à l'API est **désactivé** |
| Paiement | Stripe Connect, modèle Express, mode test — **aucune ligne avant L4** |
| Variables | `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`, `EXPO_PUBLIC_STRIPE_PK` |

**Trois conséquences que Claude Code ne devinera pas :**

1. **RLS activée sans politique ne produit pas une erreur, elle produit une liste vide.** C'est
   le piège numéro un de ce lot : un écran qui affiche « aucune donnée » alors que la donnée
   existe. Chaque table a donc un test qui prouve qu'un accès légitime rend la donnée.
2. **L'exposition automatique étant coupée, chaque migration doit accorder explicitement les
   droits** aux rôles applicatifs. Une table créée sans `grant` répond « introuvable » en
   développement alors que la migration a réussi.
3. **Le plan gratuit met un projet en veille après une semaine sans activité, et limite à deux
   projets actifs.** Dev + prod, c'est exactement le quota. Le projet de production dormira
   pendant tout le développement : c'est normal, ne mets pas de réveil artificiel. En revanche
   les migrations doivent être **rejouables de zéro**, parce que c'est comme ça que la
   production sera construite le jour venu.

Puis la preuve : commente une politique, relance, et MONTRE-MOI la sortie rouge du test
correspondant. Remets la politique. Je veux voir les deux sorties dans ta réponse. Contre ce

base locale en une seconde : politique par politique, pas un échantillon ; si un cycle échoue

Ne fabrique aucune doublure dans ce banc. Un test de politique contre une fausse base ne
teste rien.
