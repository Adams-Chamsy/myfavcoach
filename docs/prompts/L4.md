# Prompts Claude Code — lot L4 (abonnement, paiement, facturation, avis)

Prompts dans l'ordre. **Un prompt à la fois.** Après chacun : tu lances la commande de
vérification, tu regardes le résultat toi-même, et tu ne passes au suivant que si c'est vert.

Si un prompt produit autre chose que ce qui est annoncé, ne corrige pas à la main : redonne le
message d'erreur exact. Le code et la spécification doivent rester d'accord.

**Ce fichier ne code rien.** Il a été rédigé en lisant `docs/perimetre.md`, `docs/domaine.md`,
`docs/api.md`, `docs/backend.md`, `docs/modele-offres.md`, `docs/dette.md`, les fiches déjà
livrées (`docs/ecrans/L2-12-profil-coach-public.md`, `docs/ecrans/L2-13-avis.md`) et les
maquettes réelles — pas de mémoire. Chaque affirmation ci-dessous a été vérifiée dans un fichier
du dépôt avant d'être écrite ici ; là où ça n'a pas été possible (une décision d'architecture de
paiement, par exemple), c'est dit explicitement comme un point à trancher, pas comme un fait.

## Les douze points qui méritent une vraie attention, avant tout code

**Le point 11 (règles des magasins d'applications) passe avant les autres** : si son
raisonnement ne tient pas, le tunnel entier doit passer par l'achat in-app, et les points 1 à 4
perdent leur objet. Il est numéroté 11 parce qu'il a été ajouté après la première rédaction,
pas parce qu'il compte moins.

### 1. Modèle de flux Stripe : charges séparées, pas des « destination charges »

**Dérivé de la coupure des lots, pas encore écrit noir sur blanc.** `docs/api.md` §8 place
`GET /coach/identification` (statut KYC Stripe Connect) en **L5**, pas en L4. Si le paiement
d'un client devait être crédité directement au compte Connect du coach (« destination charge »,
le modèle le plus courant pour une marketplace Stripe Connect Express), ce compte devrait déjà
exister et être au moins partiellement onboardé **avant** qu'un client puisse s'abonner — ce qui
contredirait la coupure L4/L5 déjà actée.

La seule lecture cohérente avec `docs/perimetre.md` §4 est donc : **charges séparées** (« separate
charges and transfers ») — le client paie la plateforme directement (compte Stripe de la
plateforme, pas un compte Connect), `Facture` et `LigneCommission` s'écrivent à L4, et le virement
réel vers le compte Connect du coach (`Versement`, un `Transfer` Stripe) n'a lieu qu'à L5, une
fois le KYC du coach complet. Un coach non identifié auprès de Stripe peut donc avoir des abonnés
payants dès L4 — son argent s'accumule (`Solde`), il ne peut simplement pas encore le retirer.
**À confirmer explicitement avant P4.2**, pas supposé silencieusement : c'est une décision
d'architecture de paiement, pas un détail d'implémentation.

### 2. Le SDK Stripe côté mobile est une nouvelle dépendance — à demander, pas à choisir seul

`CLAUDE.md` §4 interdit d'ajouter une dépendance sans le signaler, poids et alternative à
l'appui. `docs/api.md` §7 décrit un `jetonPrestataire` remis « au module du prestataire, qui
collecte le moyen de paiement » — en pratique, `@stripe/stripe-react-native` (le SDK officiel,
seul à gérer nativement la saisie carte PCI-compliant, le mandat SEPA et l'authentification 3-D
Secure sans jamais faire transiter un numéro de carte par ce dépôt). Aucune alternative sérieuse
n'évite un module natif : un simple appel HTTP à l'API Stripe échouerait la conformité PCI DSS
dès qu'un champ de carte est saisi côté application. **Poids et confirmation à donner en P4.2**,
avant `npx expo install`.

**Tranché en P4.2 (28 septembre 2026) : pas de SDK natif. Page de paiement hébergée par Stripe
(Checkout).** L'affirmation « aucune alternative sérieuse » ci-dessus était fausse : la page
hébergée évite tout module natif ET toute saisie de carte côté application. Et le SDK natif n'a
**aucune implémentation web** (vérifié dans son paquet) — or le web est le canal du plan B si Apple
refuse (point 11). Dépendances accordées : `expo-web-browser` (application), `stripe` (Edge
Functions seulement, jamais dans le paquet mobile). Détail et raisons : `docs/backend.md` §13.

### 3. Le webhook vit dans une Supabase Edge Function, jamais dans PostgREST

Première fois que ce dépôt reçoit un appel entrant d'un tiers plutôt que d'appeler PostgREST
lui-même. `docs/api.md` §7 est explicite : les événements de paiement (succès, échec, 3DS
complété) arrivent au serveur, jamais à l'application — un `POST` signé de Stripe vers un
point d'entrée HTTP. PostgREST n'expose que des tables et fonctions Postgres, jamais un point
d'entrée qui vérifie une signature HMAC et déclenche une cascade de mises à jour transactionnelles
(`Abonnement` → `Facture` → `LigneCommission` → `Invitation.statut`, voir point 8) : c'est le
rôle d'une **Supabase Edge Function** (Deno), déjà le mécanisme envisagé par `docs/dette.md` pour
la purge à J+30 et l'export RGPD (« tâche serveur, Supabase Edge Function + cron »), jamais
encore écrit dans ce dépôt. `docs/backend.md` n'a aujourd'hui aucune section sur les Edge
Functions : P4.1 lui en ajoute une, même traitement qu'une nouvelle convention de migration.

**Secrets** : la clé secrète Stripe (`sk_test_...`) et le secret de signature du webhook
(`whsec_...`) vivent **uniquement** dans les variables d'environnement de l'Edge Function
(`supabase secrets set`), jamais dans `.env` de ce dépôt, jamais avec un préfixe `EXPO_PUBLIC_` —
même principe que `service_role` (`CLAUDE.md` §2, `eslint.config.js`, `CLE_SECRETE` bloque déjà
tout littéral commençant par `sk_test_`/`sk_live_` dans le paquet mobile : la garde existe avant
même que ce lot ne commence). Seule `EXPO_PUBLIC_STRIPE_PK` (déjà réservée dans `.env.exemple`,
vide depuis L0) rejoint le paquet mobile.

**Événements entrants : livrés plusieurs fois, dans le désordre.** Stripe réessaie un événement
tant qu'il n'a pas reçu de réponse 2xx, et ne garantit aucun ordre d'arrivée entre deux
événements (sa documentation le dit explicitement, « Handle duplicate events » et « Event
ordering »). L'`Idempotency-Key` du point 4 ne protège que les appels **sortants** (application →
serveur) ; elle ne dit rien des événements **entrants** (Stripe → serveur). Deux règles, pour le
webhook seulement :

- **Mémoriser les identifiants d'événements traités.** Une table `evenements_prestataire`
  (identifiant d'événement Stripe `evt_…` en clé unique, type, reçu le, traité le). Le
  traitement insère d'abord cet identifiant, **dans la même transaction** que les écritures
  métier qu'il déclenche : un second envoi du même événement heurte la contrainte d'unicité et
  répond 200 sans rien refaire. Une insertion hors transaction (identifiant noté, écritures
  échouées) perdrait l'événement pour de bon.
- **Ne jamais supposer un ordre d'arrivée.** Un événement est un signal « quelque chose a
  changé », pas un état à recopier : le traitement relit l'objet concerné (intention de
  paiement, facture Stripe) et ne demande que la transition que la machine de
  `docs/domaine.md` §4.3/§4.4 autorise depuis l'état **actuel** en base. Un échec qui arrive
  après un succès déjà enregistré pour la même échéance ne fait pas repasser l'abonnement en
  `impaye` ; un événement qui vise une ligne pas encore créée chez nous répond non-2xx, pour que
  Stripe le relivre plus tard, jamais 200 en l'ignorant.

**Les deux se prouvent au banc (P4.5), pas seulement à la lecture du code** : le même événement
signé livré deux fois produit une seule facture et une seule ligne de commission ; un échec
livré après le succès de la même échéance laisse l'abonnement `actif` ; deux événements livrés
dans l'ordre inverse aboutissent au même état final que dans l'ordre naturel.

### 4. `Idempotency-Key` : un mécanisme à décider, pas une promesse en-tête

`docs/api.md` §1 l'exige sur « tout POST qui déplace de l'argent », mais rien dans ce dépôt ne
la fait respecter aujourd'hui : PostgREST ne déduplique rien de lui-même. Il faut une table
dédiée (clé d'idempotence, compte appelant, réponse déjà produite le cas échéant) vérifiée par
chaque fonction concernée AVANT d'agir, jamais après — sans quoi un double-tap sur « Confirmer »
pendant un mauvais réseau crée deux abonnements. **À concevoir en P4.2**, avant la première
fonction qui en a besoin.

### 5. Une entité manque à `docs/domaine.md` : la tentative de prélèvement

La machine §4.4 (« Paiement d'une échéance ») décrit `echoue --(relance J+1)--> en_cours`, trois
tentatives, « chaque échec notifie le client avec le motif transmis par la banque » — mais
**aucune entité du §3 ne porte ces échecs**. Sans elle, l'écran 20 (Paiement refusé) n'a rien de
réel à afficher au-delà du dernier motif, et la relance à J+3/J+7 n'a aucun moyen de savoir
combien de tentatives ont déjà eu lieu. **P4.1 doit d'abord ajouter cette entité à
`docs/domaine.md`** (nom à trancher — `TentativePrelevement` semble le plus direct : `abonnement`,
`tentativeNumero` (1 à 3), `statut` (`en_cours` \| `reussie` \| `echouee`), `motifBanque?`,
`tenteeLe`) avant qu'aucune migration ne l'écrive — même discipline que pour toute autre entité
de ce fichier : la règle vit ici avant le schéma.

### 11. PRIORITÉ — Règles des magasins d'applications : ce qui autorise le paiement hors achat in-app

`CLAUDE.md` §2 et §4 fixent « aucun achat in-app » ; `docs/domaine.md` §3.3 en donne la raison
(« une offre sans engagement humain [...] serait qualifiée de contenu numérique, ce qui
imposerait l'achat in-app »). Ce point dit ce que cette raison exige du tunnel — parce que c'est
le tunnel, pas le schéma, que la personne qui examine l'application lit.

**Le raisonnement.** Le client paie un **service rendu par une personne**, pas l'accès à du
contenu numérique. C'est ce que porte `engagement_humain` (`docs/domaine.md` §3.3) : toute
offre publiée engage le coach à un geste humain réel (ajustement hebdomadaire, visio mensuelle,
messagerie avec délai de réponse annoncé). Textes applicables, lus le 28 septembre 2026 :

- Apple, *App Review Guidelines* **3.1.1** : l'achat in-app est obligatoire pour « déverrouiller
  des fonctionnalités » (« subscriptions, [...] access to premium content, or unlocking a full
  version »).
- Apple **3.1.3(d)** *Person-to-Person Services* : un paiement hors achat in-app est permis pour
  « real-time person-to-person services between two individuals (for example tutoring students,
  medical consultations, real estate tours, or fitness training) ». **One-to-few** et
  **one-to-many** restent en achat in-app.
- Apple **3.1.3(e)** : services « consumed outside of the app » → paiement hors achat in-app
  **obligatoire**.
- Google Play, *Payments policy* : Google Play Billing non requis pour les « physical services
  (such as [...] gym memberships [...]) ».

**Ce que ces textes ne disent pas, et que le raisonnement ne doit pas supposer.** 3.1.3(d) dit
*real-time*. Deux des trois engagements humains du domaine (ajustement hebdomadaire, messagerie
avec délai de réponse annoncé) sont **asynchrones** ; seule la visio mensuelle est en temps réel,
et le présentiel (`ProfilCoach.formats`) est le seul cas qui relève clairement de 3.1.3(e). Le
programme et les séances (L6) sont livrés **dans** l'application. Le raisonnement tient donc sur
la nature de l'offre prise en entier (le coach, son temps, son jugement, pas une bibliothèque),
pas sur une case unique des règles — et c'est précisément ce qu'un examinateur peut contester.
**Ce n'est pas tranché ici** : c'est inscrit dans `docs/perimetre.md` §6 comme point à faire
valider (juriste, et lecture des règles en vigueur au moment de la soumission), pas supposé
acquis. Une offre groupée (un coach, plusieurs clients en même temps) tomberait en
« one-to-many » : elle est déjà hors périmètre (`docs/perimetre.md` §3, groupe fermé), et doit le
rester pour cette raison aussi.

**Ce que le tunnel ne doit jamais faire, pour que le raisonnement tienne.** Aucune formulation
qui vende de l'**accès à du contenu** ; aucun **déverrouillage** ; aucun vocabulaire
d'**abonnement numérique**. Concrètement, dans 04a, 04b, 04c et 20 : jamais « débloquer »,
« déverrouiller », « premium », « illimité », « exclusif », « accès à / accéder au contenu »,
« bibliothèque », « VIP », « version complète ». Ce qu'on achète se nomme par le coach et son
geste : « suivi », « accompagnement », « ton coach », l'engagement humain de l'offre.
Le mot « abonnement » lui-même reste : c'est le nom du contrat récurrent dans le domaine, et le
sens d'un abonnement de salle de sport — mais il est toujours rattaché au coach (« S'abonner à
Yannick »), jamais à du contenu. La maquette 04a le montre en creux : « Programme seul — 8
semaines en autonomie, sans échange direct » est exactement du contenu numérique, et c'est
l'offre que l'arbitrage #9 a supprimée.

**Décidé le 28 septembre 2026 — point bloquant nommé, pas un risque de rédaction.** Un
abonnement dont l'essentiel est un programme écrit livré dans l'application n'est probablement
pas un service temps réel entre deux personnes. Inscrit dans `docs/perimetre.md` §6 comme point
bloquant de la soumission iOS, avec un **plan B écrit et non construit** : souscription hors
application (web), l'application iOS restant un outil de suivi. **L4 continue tel quel** : le
tunnel Stripe sert le web et Android de toute façon. Rien du plan B n'est construit dans ce lot.

**Contrainte permanente, pas une note de lot** : écrite en P4.1 dans `docs/domaine.md` §2
(règle transverse), pas seulement ici.

**Un test, sur le modèle des libellés interdits de
`src/fonctionnalites/compte/ecran-compte.test.tsx` (critère 9)** : chaque écran du tunnel (04a,
04b, 04c, 20) est rendu, et aucun terme de la liste ci-dessus n'apparaît. Une seule liste,
exportée depuis un fichier de `src/test/` et partagée par les quatre écrans, jamais recopiée
dans chacun. **Différence avec le modèle, voulue** : `ecran-compte.test.tsx` cherche dans
`JSON.stringify(screen.toJSON())`, qui contient aussi les **noms** de propriétés — un terme
comme « acces » y trouverait `accessibilityLabel`. Le test balaie donc les textes rendus et les
valeurs de `accessibilityLabel`/`accessibilityHint`, pas la sérialisation brute. Écrit au prompt
qui construit chaque écran (P4.6, P4.7), jamais après.

### 12. Réconciliation : détecter un écart entre Stripe et nos factures

Le webhook (point 3) peut manquer un événement pour de bon (déploiement en panne plus longtemps
que la fenêtre de relivraison de Stripe, bug de traitement qui répond 200 à tort), et une
écriture chez nous peut réussir sans que l'argent n'arrive. Rien, dans ce qui précède, ne le
verrait : le banc prouve que le traitement est juste **quand l'événement arrive**, jamais qu'il
est arrivé. **Mécanisme proposé, pas codé** (à valider avant P4.4, qui en dépend pour une
colonne) :

1. **Une référence commune.** Chaque `Facture` payée porte l'identifiant Stripe du paiement qui
   l'a réglée (`referencePrestataire`, unique) — champ absent de `docs/domaine.md` §3.5
   aujourd'hui, à y ajouter en P4.4 si ce mécanisme est retenu. Sans clé de jointure, aucun
   rapprochement n'est possible autrement qu'à la main, au montant et à la date.
2. **Un rapprochement quotidien**, Edge Function + cron (même mécanisme que la purge J+30,
   point 3), sur une fenêtre glissante (J-3 à J-1, pour laisser les prélèvements SEPA se
   confirmer) : la liste des paiements réussis chez Stripe sur la fenêtre, lue par l'API, face
   aux factures `payeeLe` sur la même fenêtre. Trois classes d'écart :
   - **encaissé sans facture** — un paiement Stripe réussi qu'aucune facture ne référence (le
     cas « événement perdu ») ;
   - **facture sans encaissement** — une facture marquée payée dont la référence n'existe pas,
     ou pas comme réussie, chez Stripe ;
   - **montant différent** — les deux existent, les montants divergent.
3. **Il signale, il ne corrige jamais.** Chaque écart s'écrit dans une table
   `ecarts_reconciliation` (classe, références, montants, détecté le, traité le?) et prévient
   l'équipe ; aucune facture n'est créée ni modifiée automatiquement. Raison : `Facture` est
   immuable (`docs/domaine.md` §2), une correction est une nouvelle ligne décidée par une
   personne — un correcteur automatique qui se tromperait écrirait une erreur comptable qu'on ne
   peut plus effacer.
4. **Ce qu'il ne couvre pas à L4**, à dire plutôt qu'à laisser croire : remboursements et
   oppositions bancaires (litiges) sont reportés (`docs/perimetre.md` §3, « litige et
   remboursement en application ») ; un remboursement fait à la main dans le tableau de bord
   Stripe apparaîtra comme un écart « montant différent » ou « facture sans encaissement », ce
   qui est le comportement voulu — il force un regard humain.

**Preuve attendue à la porte de sortie** (étape 11) : un paiement de test créé directement dans
Stripe, sans passer par le webhook, apparaît comme « encaissé sans facture » au rapprochement
suivant ; une facture de banc sans paiement Stripe apparaît comme « facture sans encaissement ».

## Les règles de conduite

Onze règles, cumulatives depuis L0 (voir `docs/prompts/L3bis.md` pour leur texte complet
d'origine), plus une douzième tirée du travail fait entre L3bis et L4, et une treizième tirée de
L4 lui-même (P4.4). **Les treize sont à reporter telles quelles dans les fichiers de prompts des
lots suivants.**

**1. Un point d'arrêt annoncé n'est pas optionnel.**
**2. Toute nouvelle surface va dans la galerie, exercée dans les deux thèmes.**
**3. Aucun fichier de test dans `app/`.**
**4. La preuve, pas l'affirmation.**
**5. Une politique n'est réputée testée qu'après avoir montré son rouge nommé, et ce rouge doit
venir d'une assertion, pas d'une exception du décor.**
**6. Le sens illégitime est aussi obligatoire que le sens légitime.**
**7. La machine de développement n'a pas Docker.** Le banc vise le projet de développement
distant ; la preuve « migrations rejouables de zéro » vient de la CI.
**8. Un test qui deviendra faux plus tard porte son intention dans le fichier.** Le point 8
ci-dessus (invitations → abonnee) en est l'application directe à ce lot.
**9. Un refus doit venir du mécanisme qu'on teste, jamais d'un autre qui se trouve sur le
chemin.**
**10. Une revue de fin de lot ne modifie jamais rien par elle-même — elle propose, l'application
attend une validation explicite.**
**11. Toute nouvelle table exige son grant `service_role` explicite, écrit dans la même
migration qui la crée — jamais supposé.**

**12. Toute fonction accordée à `anon` ou `authenticated`, et toute table nouvellement créée,
suivent explicitement la convention verrouillée par `src/test/conventions-grants-migrations.test.ts`
(19 septembre 2026) — jamais une convention supposée connue.** Trouvé trois fois avant que ce
test n'existe (`0006` pour anon/authenticated sur les tables, la règle 11 ci-dessus pour
`service_role` sur les tables, `0030` pour `service_role` sur les fonctions) : un `revoke ...
from public` qui omet un rôle nommé passe inaperçu contre le projet distant (baseline déjà vide)
et ne rougit que sur une pile fraîche — ou pas du tout, si aucun test n'exerce la fonction sous ce
rôle précis. Ce test balaie tout `supabase/migrations/` à chaque `npm run verif` : toute
migration de L4 doit le satisfaire du premier coup — `revoke ... from public, anon, authenticated,
service_role` avant chaque `grant`, `set search_path = public` sur chaque fonction `security
definer`, un grant `service_role` explicite sur chaque table nouvelle, y compris `abonnements`,
`factures`, `lignes_commission`, `tentatives_prelevement`, `avis`.

**13. Chaque bloc du banc prépare lui-même ce dont il dépend, et doit passer seul.** Ajoutée le
30 septembre 2026, après P4.4. Un bloc qui ne passe que dans l'ordre complet du fichier est un
faux vert en attente : il dépend d'une préparation faite ailleurs, qui peut disparaître, changer
d'ordre ou être filtrée sans que rien ne rougisse là où le défaut se trouve. Trouvé à P4.4 : le
bloc « abonnements » de P4.3 réutilisait le compte A sans créer son profil client, créé par le
`beforeAll` de `describe('profils_client')` ; `npm run verif` (ordre complet) passait, un
lancement filtré avec `-t` échouait dans sa préparation — vu seulement parce qu'il a été filtré.
Réutiliser un compte partagé reste permis (plafond de connexions) ; ce qui ne l'est plus, c'est de
supposer l'état qu'un autre bloc lui a donné : le bloc vérifie cet état et le crée s'il manque.
**Vérification qui va avec, à chaque prompt qui étend le banc** : lancer **au moins le nouveau
bloc isolément** (`npm run test:rls -- -t "<nom du bloc>"`) en plus de `npm run verif`, avant de
conclure — et **le dire dans le rapport**, avec le nombre de tests passés dans ce lancement isolé.
